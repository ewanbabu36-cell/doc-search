## 1. Statutory Data Protection & Staging Policy

Under the Digital Personal Data Protection (DPDP) Act 2023 (Section 4–9), Digital Information Security in Healthcare Act (DISHA) guidelines, and HIPAA Security Rule (45 CFR § 164.314), the transfer, replication, or processing of actual protected health information (PHI) or personal identifiable information (PII) within pre-production testing or staging environments is **strictly prohibited**.

### Core Governance Invariants Enforced in DocSearch Staging
1. **Zero Real Patient Data Invariant:** Staging databases, caches, and storage volumes must exclusively ingest and process procedurally synthesized healthcare records.
2. **Credential Segregation Invariant:** Staging infrastructure must never share or possess production database passwords, JWT signing keys, payment provider keys, or KMS encryption keys.
3. **Target Isolation Invariant:** Staging workloads must be prevented from communicating with production endpoints, live payment rails, or external hospital EMR systems.

## 2. Forensic Verification of Data Privacy Controls

### 2.1 Synthetic Patient Records & Procedural Generation
- **Clinical Fixtures:** In `scripts/docsearch-pacs-server.mjs`, all patient studies (`Kamla Devi`, `Ramesh Verma`, `Harpreet Singh`) and DICOM slices are procedurally generated by pure JavaScript mathematical equations.
- **Grayscale Synthesis:** CT skull outlines and brain parenchyma are generated via trigonometric formulas (`Math.sin(x/8) * 3 + Math.cos(y/8) * 3`), with zero input from real hospital PACS scanners.
- **Documented PII Scan:** A complete audit of `data/pacs-storage/pacs-index.json` confirmed:
  - Zero real telephone numbers.
  - Zero Aadhaar or Government ID numbers.
  - Zero postal addresses or real hospital identifiers.
  - Zero biometric or clinical telemetry from living individuals.

### 2.2 Credential Air-Gapping & Secrets Lifecycle
- **Staging vs. Production Credentials:**
  - Database master passwords, Redis auth tokens, and session encryption keys are dynamically generated per-environment using Terraform `random_password` resources.
  - In `infra/secrets_manager.tf`, secrets are namespaced under `docsearch/staging/*`, completely isolated from any `docsearch/production/*` namespace.
  - Payment gateway credentials in `payment_credentials` specify placeholder staging sandbox tokens (`rzp_staging_placeholder`), preventing accidental charges against live banking cards or UPI accounts.
- **No Hardcoded Credentials:** Inspection of the repository confirms zero plaintext passwords or AWS secret access keys committed in source code.

### 2.3 Log Sanitization & Sensitive Data Redaction
- **API Gateway Logging:** The Node.js/TypeScript API Gateway utilizes structured logging with automatic redaction rules targeting:
  - `authorization` headers (Bearer tokens).
  - `cookie` headers (session IDs).
  - `password`, `pin`, `cvv`, `otp` payload fields.
- **PostgreSQL Parameter Group:** In `infra/rds.tf`, `log_min_duration_statement = 250` logs only query execution duration for queries taking > 250ms, without logging statement parameters or patient query literals.

### 2.4 Infrastructure & Storage Isolation
- **Database Isolation:** Staging PostgreSQL runs on an independent AWS RDS instance (`docsearch-staging-primary`) in private database subnets. No database peering, replication, or shared connection pools exist between staging and production.
- **EFS Shared Storage:** Staging EFS filesystem (`docsearch-staging-pacs-efs`) is mounted strictly within staging subnets.
- **S3 Bucket Isolation:** CloudTrail and state buckets use staging-prefixed names (`docsearch-staging-cloudtrail-`, `docsearch-staging-tfstate-`), preventing cross-environment object access.
